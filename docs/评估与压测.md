# 评估与压测

本文记录 2026-11-14 在本机完成的三部分测量：自动化测试、识别质量评估、提单压测。架构见 [架构设计.md](架构设计.md)，逐条验收见 [验收核对.md](验收核对.md)，文中 FR-0xx、SC-0xx、D-0xx 指 [SPEC.md](SPEC.md) 中的编号。

## 1. 环境

| 项 | 配置 |
| --- | --- |
| 机器 | Intel Core Ultra 5 225H（14 核）、31.4 GB 内存，Windows 11 Pro |
| 数据库 | MySQL 8.0.43（本机 `MySQL80` 服务，默认配置） |
| 后端 | Python 3.13，uvicorn 单进程，与 README 的启动方式相同 |
| 文本模型 | DeepSeek `deepseek-v4-flash`，关闭思考模式 |
| 视觉模型 | 阿里云百炼 `qwen3-vl-plus` |

评估和压测脚本都会新建独立数据库（`trade_order_eval`、`trade_order_loadtest`），灌入与 README 初始化相同的示例数据，在空闲端口启动一个后端实例，结束后停止进程并删除该库，不影响业务库。

## 2. 自动化测试

`uv run pytest -q`：13 个测试文件、51 个用例全部通过，耗时 76 秒。每个用例在测试库上重建表并灌入示例数据；调用大模型的环节用固定输出代替，不消耗模型额度。

| 范围 | 用例 | 覆盖的要点 |
| --- | --- | --- |
| 对话图 | `test_chat_graph` | 12 种相对日期换算、场景一两轮对话合并、缺合同号追问、未说明单据类型时按合同类型确定、明确类型与合同不符时报错、帮助意图 |
| 物料标准化 | `test_normalizer` | 全部别名、合同首项默认、规格写在名称里、模糊写法、字典外物资不给编码 |
| 草稿校验 | `test_validator` | 合同带出与固定属性、缺失与未映射、类型不符与跨部门合同、交期规则、公允价与合同外物料 |
| 额度规则 | `test_quota` | 只有金额超额触发特批、数量超出只高亮、配额阈值、恰好用完不算超额、公允价偏离 |
| 提交事务 | `test_submit` | 同一草稿 5 次并发提交只生成 1 笔（SC-004）、同一合同 10 笔并发的额度判定（SC-003）、超额必须备注 |
| 图片识别 | `test_ocr` | 场景二映射与超额、识别不出物资、非图片文件 |
| 批量导入 | `test_batch` | 三类异常行、批内累计额度、行内修正、缺列与空文件、日期格式与模板 |
| 订单与审批 | `test_orders`、`test_resubmit` | 列表筛选与部门隔离、退回重提沿用原单号、驳回释放额度、特批通过 |
| 权限 | `test_permission` | 跨部门读订单、合同、草稿与跨部门审批均被拒（SC-007），角色越权返回 403 |
| 主数据与配置 | `test_admin` | 新增别名后对话映射生效、合同与物料增改、参数校验、审计筛选与仅管理员可用 |

## 3. 识别质量评估

脚本 [backend/scripts/eval_quality.py](../backend/scripts/eval_quality.py)，调用真实模型。

### 3.1 物料标准化

示例数据中的每个别名、每种物料的“名称 + 规格”、每个物料编码各做一次标准化，比对期望编码；另取 5 种字典外物资（门窗、PVC 管、镀锌管、防水卷材、电缆），检查不会得到任何编码。

| 输入 | 只用规则（别名、模糊匹配） | 规则分不出时交给模型挑选 |
| --- | --- | --- |
| 别名 | 120 / 120 | — |
| 名称 + 规格 | 23 / 27 | 27 / 27 |
| 物料编码 | 27 / 27 | — |
| 字典外物资 | 5 / 5 未给编码 | — |

规则没有直接定下的 4 条是盘螺 Φ8、Φ10 和热轧钢板 10 mm、20 mm。同一品类各规格的名称相同，规格里还有共同的数字（HRB400E 的 400、Q235B 的 235），模糊匹配给出的分差达不到直接采用的门槛；其中钢板 20 mm 一条，得分最高的候选反而是 10 mm。正式流程在这一步把前 5 个候选交给 DeepSeek 挑选，返回值必须属于候选，4 条全部选对。全部输入中没有出现物料字典之外的编码（C-002）。

### 3.2 对话抽取

20 条首轮提单语句覆盖：只写品类不写规格、俗称（“三级螺纹16”“25螺”“四二五水泥”）、中文数字（“一百吨”）、小数数量、一句多种物资、写明单价，以及后天、大后天、3天内、下周三、周三、月底、下下周一、具体日期等交期说法。每条经 `/api/chat` 生成草稿后逐字段比对。

| 字段 | 正确 |
| --- | --- |
| 合同号 | 20 / 20 |
| 物料编码与数量 | 20 / 20 |
| 交期 | 20 / 20 |
| 单价（2 条写明单价） | 2 / 2 |
| 单据类型 | 20 / 20 |
| 全部字段正确 | 20 / 20 |

单轮响应 p50 0.91 秒、p95 1.63 秒。

首次评估时单据类型只对了 17 条。错的 3 条都关联采购合同，但语句里没有“采购”“进货”字样（如“2026-CG-031 补 P.O42.5 散装水泥 200 吨，周三到”）：抽取结果没有单据类型，草稿沿用默认的销售类型，随后校验报“合同 2026-CG-031 是采购合同，不能用于销售订单”。按 D-022 修改后，用户本轮没有表明类型、又关联了新的合同时，单据类型按合同类型确定，与图片识别一致；上表为修改后重跑的结果。用户明确说了销售却给出采购合同时，仍报类型不符。

### 3.3 单据图片识别

样例发货签收单（42.5 水泥 500 吨、金额 22 万元，合同 2026-CG-031）原图加四种变体，经 `/api/ocr` 识别，比对合同号、物料编码、数量、金额。

| 变体 | 结果 |
| --- | --- |
| 原图 | 4 项全对 |
| 缩小一半（700×490） | 4 项全对 |
| JPEG 质量 30 | 4 项全对 |
| 旋转 5 度 | 4 项全对 |
| 灰度 | 4 项全对 |

单次识别 p50 3.54 秒、最长 4.09 秒。样例只有一张单据，变体只检验了画质与角度的影响，不代表对不同版式单据的识别率。

## 4. 提单压测

脚本 [backend/scripts/load_test.py](../backend/scripts/load_test.py)，客户端与后端在同一台机器上，用 httpx 异步并发发请求。

### 4.1 提交吞吐

每档预先保存 40 份草稿（同一销售合同 2026-WZ-089、各 1 吨，单价取合同价），再按并发上限提交。

| 并发 | 成功 | 单号唯一 | 总耗时（秒） | 吞吐（笔/秒） | 延迟 p50 / p95 / 最大（ms） |
| --- | --- | --- | --- | --- | --- |
| 1 | 40/40 | 是 | 0.52 | 76.8 | 12.8 / 14.6 / 19.3 |
| 4 | 40/40 | 是 | 0.42 | 94.6 | 40.6 / 48.3 / 50.5 |
| 8 | 40/40 | 是 | 0.43 | 92.2 | 82.4 / 95.6 / 99.6 |
| 16 | 40/40 | 是 | 0.45 | 88.4 | 159.8 / 185.4 / 207.4 |

吞吐在并发 4 时到顶，约每秒 90 笔；之后延迟随并发线性增长，相当于每笔约 11 ms 的串行处理时间。提交事务依次锁草稿行、合同行和单号流水行（C-003），同一合同的提交在合同行锁上排队，同一单位同一天的单号又共用一行流水，所以这条路径是串行的，加并发只会加长排队。这是有意的取舍：额度判定和单号连续性依赖这两把锁。不同合同的提交同样要过单号流水行，因此换成多合同也不会明显提升吞吐。

### 4.2 正确性

| 场景 | 做法 | 结果 |
| --- | --- | --- |
| 重复提交（SC-004） | 20 份草稿各同时发 5 次提交，共 100 个请求一起发出 | 只生成 20 笔订单，同一草稿 5 次响应单号相同，无错误；延迟 p50 290 ms、最大 438 ms |
| 额度争抢（SC-003） | 采购合同 2026-CG-031 剩余 150,000 元，40 份各 22,000 元的草稿同时提交 | 6 笔为已提交，34 笔为待特批；按单号先后逐笔复算，每笔的超额判定都与复算一致 |

两组请求都一次全部发出、不限并发，没有任何请求失败。

### 4.3 读取接口

订单列表、订单详情、合同详情（含额度汇总）三个接口轮流请求，每档共 300 次。

| 并发 | 每秒请求 | 错误 | 全部 p50 / p95 / 最大（ms） | 订单列表 p95 | 订单详情 p95 | 合同详情 p95 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 137.3 | 0 | 7.1 / 9.1 / 11.1 | 8.2 | 9.8 | 7.7 |
| 8 | 222.9 | 0 | 33.8 / 48.9 / 65.8 | 38.7 | 53.1 | 42.7 |
| 32 | 237.3 | 0 | 123.9 / 260.0 / 518.4 | 258.4 | 290.3 | 283.4 |

单进程 uvicorn 在并发 8 左右接近上限，每秒约 230 次请求；再加并发只增加排队。演示规模（一个部门几名经办人和审批人）下，接口延迟在 10 ms 量级。

### 4.4 批量导入

上传 500 行全部合法的 Excel（单次上限），三种螺纹钢轮换、各 1 吨。

| 步骤 | 耗时 | 结果 |
| --- | --- | --- |
| 上传、解析与整批校验 | 6.61 秒 | 500 行全部为可提交 |
| 批量提交 | 16.04 秒 | 500 行全部成功，每秒 31.2 行 |

批量提交比 4.1 节的接口提交慢，是因为 500 行属于同一合同，按设计逐行串行提交（DESIGN 4.3），保证提交时的超额判定与校验时的批内累计一致；每行还要先建一份草稿再走完整提交事务。

### 4.5 对话响应时间（SC-008）

三种首轮提单语句轮换，并发 1 与 4 各发 12 次，调用真实 DeepSeek。

| 并发 | 失败 | 总耗时（秒） | 延迟 p50 / p95 / 最大（ms） | 15 秒内返回 |
| --- | --- | --- | --- | --- |
| 1 | 0 | 13.2 | 974 / 1785 / 1785 | 12/12 |
| 4 | 0 | 4.15 | 1177 / 1781 / 1781 | 12/12 |

对话耗时几乎全部是模型接口的响应时间，并发 4 时单轮延迟基本不变，总耗时缩短到约三分之一。连同 3.2 节的 20 次，三组共 44 次对话请求，最长 1.79 秒，SC-008 要求 15 秒内。

## 5. 结论与改进方向

- 正确性：并发提交、重复提交、额度争抢三类场景结果都与逐笔计算一致，行锁和唯一索引的设计成立。
- 性能：单进程后端每秒约 90 笔提交、约 230 次读取，对话单轮 1～2 秒，满足课程演示与单部门使用；瓶颈分别在合同与单号的行锁、单进程事件循环、模型接口。
- 识别：物料映射在模型挑选兜底后全部正确，且没有字典外编码；对话抽取的单据类型、合同号、物料、数量、交期、单价全部正确；图片识别在四种画质变体下稳定。
- 待改进（均未实现）：单号流水改为按日预分配号段，减少同一行上的锁等待；读取接口在多进程部署（`uvicorn --workers`）下复测。

## 6. 复现

在 `backend` 目录执行，需要 MySQL 已启动、`.env` 已配置：

```powershell
uv run pytest -q
```

```powershell
uv run python -m scripts.eval_quality --out eval.json
```

```powershell
uv run python -m scripts.load_test --levels 1,4,8,16 --orders 40 --batch-rows 500 --chat 12 --out lt.json
```

`eval_quality` 加 `--skip-llm` 只跑物料标准化；`load_test` 的 `--chat 0` 跳过对话阶段。两个脚本都会调用真实模型（约 30 次文本请求、5 次视觉请求），会消耗少量额度。
