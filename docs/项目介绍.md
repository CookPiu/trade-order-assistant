# 智能商贸提单助手 项目介绍

本文是项目的全景介绍：解决什么问题、给谁用、能做什么、一次提单怎么走、技术怎么选、关键取舍和实测结果。分层与流程见 [架构设计.md](架构设计.md)，测量数据见 [评估与压测.md](评估与压测.md)，逐条验收见 [验收核对.md](验收核对.md)；文中 FR、SC、D 编号均指 [SPEC.md](SPEC.md)。

## 1. 背景与目标

大宗商贸（钢材、水泥等建材）的业务经办人每天要把客户的口头需求、发货签收单、整理好的表格录进商贸系统，形成销售或采购订单。传统录单要手工查合同、对物料编码、算剩余额度，容易录错编码或超出合同额度。

本项目是课程“项目实战 2.10”的实现（需求原文 [需求说明.md](需求说明.md)）：经办人用一句话、一张单据照片或一份 Excel 生成订单草稿，系统自动关联合同、把物资俗称映射为标准物料编码、核验合同履约额度，经办人核对后一键提交到商贸系统；超额订单转审批人特批。

验收要求的两个示例场景都能从输入跑到正式订单号：

- **场景一**：输入“给中建八局科技城项目下 200 吨 HRB400E 螺纹钢，走 2026-WZ-089 合同，后天送到一号工地”，生成销售订单，物料映射为 `STL-RB-400E-20`，交期为后天。
- **场景二**：上传一张手写的发货签收单（42.5 水泥 500 吨、22 万元），识别后发现超出采购合同剩余额度，填写备注后提交，订单进入待特批。

## 2. 用户与角色

| 角色 | 账号示例 | 做什么 |
| --- | --- | --- |
| 业务经办人 | `jbr01` | 对话、图片、Excel 三种方式提单；查看本部门订单；修改被退回的订单后重提 |
| 业务审批人 | `spr01` | 在订单详情中审核通过、退回修改或驳回本部门已提交、待特批的订单 |
| 系统管理员 | `admin` | 维护合同台账、物料字典与别名、额度与模型参数，查看审计日志 |

数据按部门隔离：示例数据有物资贸易公司和建材贸易公司两个部门，一方的经办人和审批人看不到另一方的订单和合同。

## 4. 一次提单怎么走

以场景一为例：

1. 经办人在工作台发送那句话。后端把当前草稿摘要和这句话交给 DeepSeek，模型按 JSON 返回意图（新建销售订单）、合同号、项目、交期原文“后天”、物资“HRB400E 螺纹钢 200 吨”。
2. 服务端把“后天”换算为具体日期，合并进草稿。
3. 物料标准化：“HRB400E 螺纹钢”没有写直径，合同 2026-WZ-089 里 Φ20、Φ16、Φ25 三种螺纹钢得分并列，描述里没有能区分它们的数字，于是取合同首项 Φ20，回复中说明并保留候选供切换（D-020）。
4. 装配：从合同带出签约单位、项目、完整收货地址和联系人，写入固定业务属性和经办人信息；没给单价，取合同约定单价 3,650 元并在字段旁注明来源（D-019）；汇总合同已下金额，算出本次占用和剩余额度。
5. 回复列出识别结果，右侧预览区显示状态胶囊、额度卡片、基本信息和产品明细。经办人也可以直接在预览区改字段，改完重新校验。
6. 点击“一键提单”。服务端锁住草稿和合同，重新核验额度，生成单号 `XSDD-WZGS-20261114-001`，写入订单、模拟商贸系统和审计日志。订单列表收到事件后刷新。

场景二的区别在第 1 步和第 6 步：字段来自视觉模型对单据图片的识别；提交时本次金额超过合同剩余额度，必须填写备注，订单状态为待特批，由审批人决定是否放行。

## 5. 技术栈

| 部分 | 选型 | 为什么 |
| --- | --- | --- |
| 后端 | Python 3.12+、FastAPI、SQLAlchemy 2 异步、uv | 接口大部分时间在等模型响应和数据库，异步单进程即可支撑演示规模 |
| 对话编排 | LangGraph | 多轮提单是“抽取、合并、标准化、装配、回复”的固定流程，图结构便于加分支（帮助意图）和单独测试节点 |
| 文本模型 | DeepSeek，OpenAI 兼容接口，JSON 输出，关闭思考模式 | 中文抽取效果好；关闭思考后单轮约 1～2 秒 |
| 视觉模型 | 阿里云百炼 `qwen3-vl-plus` | 直接输出结构化字段，不需要单独部署 OCR（D-002），手写体也能识别 |
| 数据库 | MySQL 8 | 额度核验依赖行锁和事务（C-003） |
| 物料匹配 | rapidfuzz | 别名未命中时召回候选 |
| Excel | openpyxl | 模板生成与解析 |
| 前端 | Vue 3、Vite、TypeScript、Element Plus、Pinia | 表格、表单、抽屉组件现成；Pinia 让悬浮窗与工作台共用状态 |

## 7. 关键设计取舍

| 问题 | 做法 | 依据 |
| --- | --- | --- |
| 大模型输出不稳定，怎么保证编码和额度正确 | 模型只做字段抽取和候选挑选；编码、额度、超额、单号、状态由数据库和规则决定 | C-002 |
| 超额了怎么办 | 允许带备注提交，进入待特批，由审批人决定，而不是直接禁止 | D-003 |
| 哪些状态占额度 | 驳回之外都占；退回期间保留，重提时排除自身占用 | D-009 |
| 并发提交会不会共用同一份额度 | 合同行加锁，锁内用 READ COMMITTED 重新汇总；单号流水同事务加锁 | C-003 |
| 一句话没写直径怎么映射 | 合同内候选并列时取合同首项，回复中说明并保留候选 | D-020 |
| 缺单价怎么办 | 对话和图片取合同约定单价并注明；Excel 是整理好的数据，缺单价作为异常暴露 | D-019 |
| 退回订单怎么改 | 重新打开原草稿，提交时沿用原单号 | D-010 |
| 悬浮窗放多少东西 | 对话加精简卡片，完整编辑去全屏工作台 | D-017 |
| 底层商贸系统怎么对接 | 项目内模拟订单表和列表页，提交时同事务写入 | D-001 |

## 9. 局限与改进方向

- 对话中用户没有说明单据类型、合同又是采购合同时，草稿会先按销售类型生成并提示类型不符，需要手动改；图片识别已按合同类型确定，对话流程可以照此处理（[评估与压测 3.2](评估与压测.md#32-对话抽取)）。
- 模型调用失败时不做规则回退，草稿保持原样，由预览区手工编辑兜底（D-008）。
- 图片识别只用一张样例单据评估过，不同版式单据的识别率没有系统测量。
- 单进程部署，同一单位同一天的单号共用一行流水锁，提交吞吐约每秒 90 笔；更高负载需要多进程部署和号段预分配。
- 不对接真实商贸系统，没有用户注册、找回密码和单点登录，不提供 Docker 部署（D-013）。
