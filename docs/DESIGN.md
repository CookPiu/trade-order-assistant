# 智能商贸提单助手 实现方案

需求原文见 [需求说明.md](需求说明.md)（项目实战 2.10），范围、需求编号与决策记录见 [SPEC.md](SPEC.md)。

## 1. 技术栈

| 层 | 选型 | 说明 |
| --- | --- | --- |
| 后端 | Python 3.12 + FastAPI + SQLAlchemy 2（async）+ uv | 与 data_agent、Dianshangxiaoer 一致 |
| 对话编排 | LangGraph | 多轮提单是“抽取 → 补全 → 核验 → 追问”的循环，用图管理会话状态 |
| 文本大模型 | DeepSeek（OpenAI 兼容接口） | 实体抽取用 JSON 结构化输出 |
| 单据识别 | 阿里云百炼 qwen3-vl-plus（OpenAI 兼容接口 `/compatible-mode/v1`；本机账号下 qwen3-vl-flash 返回模型不存在） | 直接输出结构化 JSON，不单独部署 OCR |
| 数据库 | MySQL 8（本机已装 MySQL80 服务） | 额度核验需要行锁和事务，SQLite 不合适 |
| Excel | openpyxl | 模板下载与逐行解析 |
| 物料模糊匹配 | rapidfuzz | 别名表未命中时做候选召回 |
| 前端 | Vue 3 + Vite + TypeScript + Element Plus + Pinia | 表单、表格、抽屉组件现成 |

假设：本地 MySQL 服务手动启动；大模型密钥只放 `.env`。

## 3. 数据模型

| 表 | 关键字段 |
| --- | --- |
| `dept`、`user` | 部门、角色（operator / approver / admin），密码哈希 |
| `party`、`project` | 签约单位（`kind` 区分客户与供应商）、工程项目、收货地址、联系人 |
| `contract` | 合同号、类型（sales / purchase）、对方单位、项目、总金额、总数量、到期日 `expire_date`、经办部门、`version`（乐观锁备用） |
| `contract_item` | 合同物料明细：物料编码、合同单价、合同数量 |
| `material` | 标准物料编码、规范名称、规格、主计量单位、品牌、公允价 `fair_price` |
| `material_alias` | 别名 / 俗称 / 简称 → 物料编码 |
| `draft` | 会话关联、草稿 JSON、状态、缺失字段列表、`idempotency_key` |
| `order` / `order_item` | 正式订单主档与明细，`draft_id` 唯一索引，`over_quota` 标记、备注、审批意见 |
| `order_no_seq` | 按（单据前缀，单位代码，日期）维护流水号 |
| `trade_sales_order` / `trade_purchase_order` | 模拟“底层商贸系统”的订单表 |
| `import_batch` / `import_row` | Excel 导入批次（文件名、导入人、时间、行数统计）与逐行解析结果、生成的订单号 |
| `audit_log` | 操作人、动作、输入原文或图片 SHA-256、单据号、时间 |
| `system_param` | 固定业务属性、公允价允许偏离比例、履约配额阈值（剩余金额占比）、模型参数 |

合同额度不单独存累计值，按 `order` 实时汇总（驳回状态的订单不计入，D-009）：已下数量、已下金额、剩余数量、剩余金额四项，正好对应预览区四张统计卡片。

“剩余可下订单数”按剩余可下数量（主计量单位，如吨）计算；只有金额超出触发超额，数量超出只做异常高亮（D-007）。

## 4. 后端核心逻辑

### 4.1 对话提单图（LangGraph）

```
extract ─帮助/闲聊→ help
   └─其他→ merge → normalize_material → link_contract → respond
```

图中实际节点如上：意图与字段在 `extract` 一次抽出；`merge` 把本轮结果合并进草稿并换算相对日期；合同带出、额度核验和草稿装配都在 `link_contract` 调用的 `draft_validator.assemble` 中完成。下面按处理步骤说明：

- `intent`：识别新建销售 / 新建采购 / 修改草稿 / 继续上次 / 帮助。
- `extract`：大模型按 JSON schema 输出合同号、项目、品名、规格、数量、单位、单价、交期；相对日期（“后天”）在服务端按当前日期换算，不交给模型算。
- `normalize_material`：先查别名表精确匹配；未命中时用 rapidfuzz 在“该合同的物料明细”里召回前 5 个候选，得分明显领先时直接采用；候选并列且描述里没有能区分候选的规格数字时取合同首项物料（D-020）；仍无法确定时让模型在候选中选一个，返回值必须属于候选；都不行则标记待确认，不允许模型编造物料编码。
- `link_contract`：按合同号查主数据，补全签约单位、项目、收货地址、经办人、经办单位；写入固定属性（国内传统贸易 / 直发 / 传统贸易）。
- `quota_check`：计算四项额度，本次金额超出剩余金额时置 `over_quota=true`；数量超出剩余数量、交期早于今天或晚于合同 `expire_date` 时加入异常字段列表（FR-023、FR-025）；单价偏离公允价超出允许比例、提交后剩余金额占比低于配额阈值时加入提醒列表，前端黄色显示，不阻止提交（FR-027、FR-028）。缺单价时先用金额除以数量，再取合同约定单价，Excel 导入关闭后一步（FR-029、D-019）。
- `respond`：必填字段缺失时在回复里逐项追问，并把缺失字段列表返回给前端做高亮。
- 单据类型（D-022）：抽取只在用户本轮表明销售或采购时给出 `order_type`，否则为空、沿用当前草稿。本轮没有表明类型且关联了新的合同时，`normalize_material` 按合同类型设定单据类型，回复中说明“已按合同设为采购订单”；用户明确表明的类型与合同不符时不改，由校验报类型不符（FR-024）。

会话状态以 `draft` 表为准：每轮从数据库载入当前草稿，执行一次图后写回，不使用 LangGraph checkpointer；对话记录由前端保存在 sessionStorage。抽取调用关闭思考模式，模型请求默认不走系统代理（`LLM_USE_SYSTEM_PROXY`），本机实测经本地代理转发时请求超时，直连单轮约 2 秒。

### 4.2 单据图片识别

上传图片 → 计算 SHA-256 → 调视觉模型，提示词限定输出字段（单据类型、物资名称、规格、数量、单位、金额、到货单位）→ 结果走与对话相同的 `normalize_material`、`link_contract`、`quota_check` → 返回识别卡片和草稿。

- 接口 `POST /api/ocr` 只识别和装配，不落库；经办人点击识别卡片上的“应用为草稿”后，前端调用草稿保存接口新建草稿，识别回复写入对话流。
- 服务端用 Pillow 校验图片格式（JPG、PNG）和大小（不超过 10 MB）；识别不出任何物资时返回 422 提示重新上传，不生成草稿。识别动作无论成败都写审计日志（图片 SHA-256、文件名、物资行数）。
- 单据上的合同号存在且属于本部门时，订单类型取合同类型；否则取模型判断，默认采购。
- 单据日期不作为交期，单据备注只显示在卡片上，不写入草稿备注，超额备注由经办人填写。

### 4.3 Excel 批量

1. 提供模板下载，一行一笔单物资订单（D-011），固定列：单据类型、合同号、物料名称、规格、数量、单价、交期、备注）。
2. 逐行解析，每行独立校验：合同存在且属于本部门、物料可映射、数量大于 0、单价存在、交期不早于今天且不晚于合同到期日。
3. 同一合同在一批里出现多行时，按行顺序累计占用额度，后面的行基于前面行占用后的剩余额度判断是否超额。
4. 前端展示校验结果表，异常行标红，可行内修改后重新校验该行。
5. 批量提交：`asyncio` 加信号量并发，每行一个事务。

实现约定：

- 模板第一个工作表为数据，列名必须包含单据类型、合同编号、物料名称、数量、单价、交期（规格、备注可缺省），缺列时整份拒绝并列出缺少的列；全空行跳过；单次最多 500 行。
- 行状态：`ok` 可提交、`over` 超额且已填备注（提交后为待特批）、`error` 异常、`submitted` 已提交、`failed` 提交失败。超额但备注为空的行记为 `error`，原因显示在备注字段上。
- 只有 `ok`、`over` 行计入批内累计占用；已提交行的订单已在数据库中计入，不重复累计。
- 物料映射只用别名和模糊匹配，不调用模型，结果不确定时给出候选，由经办人行内选择。
- 行内修改会影响同一合同后续行的累计额度，因此保存一行后整批重新校验；提交前也先整批重新校验一次。
- 提交时不同合同的行并发，同一合同的行按行号串行，使提交时的超额判定与校验时的批内累计一致。每行先建一条草稿（`session_id = batch-<批次号>`），再走与对话提单相同的提交事务，订单来源记为 `excel`。

### 4.4 提交与幂等

- 提交事务内对合同行执行 `SELECT ... FOR UPDATE`，重新计算额度，防止并发提交同时占用同一份剩余额度。数据库连接使用 READ COMMITTED 隔离级别：MySQL 默认的 REPEATABLE READ 会让加锁后的额度汇总读到事务开始时的旧快照，导致并发提交漏判超额。
- 超额订单必须带备注，状态置为“待特批”（`pending_special`），否则置为“已提交”。
- `order.draft_id` 唯一索引兜底防重；重复请求返回已生成的订单号。
- 退回订单重提沿用原单号（D-010）：同样先锁合同行，计算剩余额度时排除该订单自身原占用，按结果置为已提交或待特批，并更新 `trade_*` 中的对应记录。
- 单号格式 `XSDD-WZGS-20260318-001`：前缀 XSDD（销售）/ CGDD（采购），单位代码取经办单位，流水号在 `order_no_seq` 上加行锁递增。
- 正式订单写入后同步到 `trade_*` 表（同一事务），并记审计日志。

### 4.5 状态流转

```
草稿未提交(draft) ─缺字段→ 待确认(pending_confirm) ─补齐→ 草稿未提交
草稿未提交 ─提交→ 已提交(submitted) ─审批→ 已审核(approved) / 退回(returned) / 驳回(rejected)
草稿未提交 ─超额提交→ 待特批(pending_special) ─审批→ 同上
退回(returned) ─经办人修改重提（原单号）→ 已提交 / 待特批
```

驳回为终态，驳回后释放额度；退回期间额度保留（D-009）。退回与驳回必须填写审批意见。

### 4.6 权限

JWT 登录。提单、提交、查询接口统一校验 `order.dept_id == user.dept_id`；审批人只能看本部门待审单据；管理员维护主数据、参数并查看审计日志。

审批人的订单列表只返回本部门已提交、待特批的订单；详情接口对本部门订单都开放，审批后仍能在抽屉中看到处理结果。审批接口 `POST /api/orders/{id}/approve|return|reject` 对订单行加锁，只处理已提交、待特批状态，退回和驳回必须带意见，结果同步到 `trade_*` 表并记审计日志（审计明细含意见与原状态）。

退回重提的实现：经办人在抽屉中点击“修改”调用 `POST /api/orders/{id}/edit`，把该订单对应的草稿重新打开（草稿保留 `order_id`），载入工作台。草稿在保存、对话修改和展示时计算额度都排除该订单原有占用；提交时 `submit_draft` 发现草稿关联的订单处于退回状态，就转入 `resubmit_order`，沿用原单号更新订单、`trade_*` 记录和草稿状态。

### 4.7 主数据与系统配置

主数据接口 `/api/admin/*`、参数接口 `/api/params`、审计接口 `/api/audit` 只对系统管理员开放。管理员维护全部部门的合同（表单中选择所属部门），经办人和审批人仍按部门读取。

- 合同：新增和修改时签约单位、工程项目按名称查找，不存在就新建，项目的地址和联系人随合同表单更新。明细物料编码必须在物料字典中，同一合同不重复。修改时对合同行加 `FOR UPDATE`，与提交时的合同行锁互斥；明细按物料编码对齐增改删，`version` 加 1。已提交订单的金额不随合同修改变化。
- 物料：编码新增时转大写，之后不能修改（已被合同和订单引用）；公允价可为空，为空时不做偏离提醒。
- 别名：对应的物料编码必须在字典中；按标准化使用的同一规则（NFKC、小写、去空格和符号）查重。标准化每次请求都从数据库读取别名，保存后下一轮对话即生效。
- 参数：`fixed_attrs`、`fair_price_deviation`（0–1]、`quota_warn_ratio`[0–1)、`llm`、`vision` 按各自结构校验后写入 `system_param`；模型温度 0–2，超时 5–300 秒。
- 审计：主数据修改记 `master_update`，明细含实体、操作、键和修改前后的值；参数修改记 `param_update`，含修改前后的值。审计查询按操作人（账号）、动作（可多选）、日期范围（按 `created_at`）和单据编号筛选，分页返回。

## 5. 前端

页面构成与各区域内容见 SPEC.md“页面”一节。

- 路由：`/login`、`/trade/orders`（模拟商贸系统订单列表，右下角挂悬浮窗）、`/workbench`（全屏工作台）、`/batch`（批量导入与导入记录）、`/admin`（主数据、参数、审计日志）。路由守卫按角色过滤导航，无权访问时跳到角色默认页（FR-045）。
- 悬浮窗和全屏工作台使用同一套 Pinia store（会话、草稿），切换时状态不丢；store 同时写 `sessionStorage`，刷新后恢复。悬浮窗只渲染精简草稿卡片组件 `DraftMiniCard`，全屏渲染完整 `DraftPreview`（D-017）。
- 悬浮窗提交成功后通过事件总线发出 `order:created`，订单列表收到后刷新并可打开详情抽屉。事件总线接口按 `postMessage` 的消息格式设计，以后改成 iframe 嵌入第三方系统时只换传输层。
- 订单列表与详情接口 `GET /api/orders`、`GET /api/orders/{id}` 读取 `order` 表并按部门过滤，经办人和审批人都可访问；`trade_*` 表保存同步给底层商贸系统的快照，不用于页面查询。详情的额度看板中“累计已下”不含本单，审计流水按单号取审计日志。
- 事件总线（`src/bus/orderBus.ts`）用 `window.postMessage` 在本窗口投递 `{source, type, payload}`，按 origin 和 source 过滤；草稿 store 提交成功后发出，工作台提交同样会触发。列表收到后切到对应页签、回到第一页并标出新订单。
- 悬浮窗展开状态写入 `sessionStorage`；工作台“切到悬浮窗”跳到 `/trade/orders?widget=open`。
- 详情抽屉 `OrderDrawer` 按角色渲染底部操作：审批人显示通过、退回、驳回（D-015），经办人对退回订单显示“修改”，点击后把订单载入 draft store 并跳转工作台（FR-038）。
- 预览区：状态胶囊、四张额度卡片、超额红色横幅、黄色提醒、基本信息网格、产品明细表、提交栏；缺失或异常字段加红框并显示原因；提交成功后按钮锁定。
- 主题：在 `src/styles/theme.scss` 覆盖 Element Plus 的 CSS 变量，浅色商务蓝，不做暗色模式（D-018）。
- 导入记录：后端新增 `import_batch`、`import_row` 两张表保存批次与逐行结果（D-016）。

## 6. 示例数据与演示

`scripts/seed.py` 生成：

- 两个部门、三类角色各一个用户；
- 销售合同 `2026-WZ-089`（中建八局科技城项目，含物料 `STL-RB-400E-20`，余额充足）；
- 一份采购合同，剩余可下金额 15 万元，物料含 42.5 水泥；

- 一份 10 行左右的批量 Excel，其中故意放入合同号错误、单价缺失、超额三类异常行。

`seed.py` 可重复执行，不产生重复数据；README 写明本机启动步骤，不提供 Docker（D-013）。

演示两条链路都覆盖：场景一走自然语言提单，场景二走图片识别加超额预警，另外用 Excel 验证批量提单。
